WHY THIS FILE EXISTS
--------------------------------------------------------------------------------
A binary in a package is anonymous. This file is how anyone later can tell which
executable came from which source, which toolchain and which build machine -
without which "rebuild it and see if it matches" is not a question that can even
be asked. Every time a binary is adopted into ../../native_libraries/<rid>/, its
section here is updated from that build's output/<rid>/BUILD-INFO.txt and the
wasm-opt.provenance.txt beside the binary is written from the same values.

DIFFERENCES FROM UPSTREAM'S RELEASE BUILD
================================================================================
Upstream's release binaries come from its .github/workflows/
create_release.yml (read at version_133 in the release archive; that folder
is not kept in this repository - see UPSTREAM.txt). What it does, and where this
folder's builds differ:

  Linux, upstream : job build-alpine on ubuntu-latest and ubuntu-24.04-arm, in
                    a node:lts-alpine container: musl libc, Alpine's GCC,
                    -DCMAKE_C_FLAGS=-static -DCMAKE_CXX_FLAGS=-static
                    (a FULLY STATIC executable), -DBUILD_SHARED_LIBS=OFF,
                    -DBUILD_MIMALLOC=ON (mimalloc, because musl's allocator is
                    slow under many threads), -Wl,-z,stack-size=8388608,
                    everything else default; builds and installs ALL tools,
                    runs the full check.py test suite, then `strip`.
  Linux, here     : manylinux_2_28 (AlmaLinux 8, glibc 2.28), GCC 14.2.1,
                    glibc linked DYNAMICALLY (floor 2.25 referenced), libstdc++
                    and libgcc STATIC; glibc's own allocator (mimalloc is a
                    submodule, absent, and glibc's malloc does not have musl's
                    multi-threading problem); the same 8 MB main-thread stack.
                    Reason: the CodeBrix Linux natives all come from one pinned
                    manylinux userland, and a glibc-dynamic executable behaves
                    like every other program on the user's system (locale, DNS,
                    allocator) while still starting on Debian 10 / Ubuntu 20.04
                    / RHEL 8 and newer.
  Every platform  : * wasm-opt target ONLY (upstream: every tool and libbinaryen,
                      `--target install`);
                    * BUILD_TESTS=OFF (gtest is an absent submodule) and no
                      check.py - the functional gate (gate-fixture.wat, the
                      consumer's flag sets, --fuzz-exec) is run instead.
                      Upstream's own test suite was NOT run on these binaries;
                    * ENABLE_WERROR=OFF (upstream: default ON) - warnings are
                      counted instead (0 on linux-x64);
                    * BUILD_SHARED_LIBS=OFF stated on every platform - upstream's
                      macOS release leaves the Unix default ON, so its macOS
                      wasm-opt loads @rpath/libbinaryen.dylib from ../lib; ours
                      is one self-contained file (MSVC forces static anyway);
                    * CMAKE_SKIP_RPATH=ON - no $ORIGIN/../lib (Linux) or
                      @loader_path/../lib (macOS) run path, since nothing lives
                      there;
                    * -ffile-prefix-map (Linux, macOS), -Wl,--build-id=sha1 and
                      a linker map file (Linux) - no effect on generated code;
                    * stripping: Linux `strip --strip-all` (upstream `strip`, the
                      same thing for an executable); macOS `strip` + ad-hoc
                      codesign (upstream `strip -x`, which keeps the global
                      symbols, and no re-sign); Windows: no symbols are emitted
                      in Release, as upstream.
  Unchanged       : CMAKE_BUILD_TYPE=Release, BUILD_LLVM_DWARF=ON,
                    BYN_ENABLE_ASSERTIONS=ON (upstream ships assertions enabled,
                    and so do we), Ninja (upstream macOS; upstream Windows uses
                    the Visual Studio generator), the static MSVC runtime
                    (binaryen's CMakeLists selects it for non-Debug MSVC
                    builds), the macOS arm64 deployment floor 11.0 and the
                    system libc++.
  Changed, macOS  : the x86_64 deployment floor is 11.0 here, 10.15 upstream
                    (see macOS above: current Xcode's libc++ supports 11.0 and
                    newer only).
